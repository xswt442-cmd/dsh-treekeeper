# dsh-treekeeper

[![Awesome DSH Plugin](https://awesome-dsh-plugin.com/badge.svg)](https://awesome-dsh-plugin.com)

**账本 ↔ 操作系统对账引擎 + 统一治理台。** DeepSeek Harness 的任务账本（后台 jobs、子代理谱系）说在跑的东西，和 OS 里真实活着的进程树，对得上吗？对不上的——泄漏的 MCP 服务器、孤儿 npx 链、无主常驻进程——归谁、养了多久、该不该杀，一次看清，守卫式一键处理。

[English](README.en.md) | 中文

## 为什么需要它

- **后台任务没有进程视角**：`JobSnapshot` 有归属会话却没有 pid，后台 bash 和子代理跑没跑干净、在系统里变成了哪些进程，账本不说。
- **子进程会泄漏**：同一个 MCP 服务器被反复拉起、旧的从不退出，几十个 node/cmd 白吃内存——没有工具能"看到这件事正在发生"。
- **插件在养进程**：每个识图/MCP/终端插件都可能留下常驻子进程，装前没人告诉你，装后没人替你盘点。

## 它做什么

- **进程树归属**：周期采样本机进程，沿祖先链归到 harness 根；每个进程标注归属（harness / 某插件 / 未归属）、内存、存活时长；
- **泄漏启发式**：相同命令行 ≥N 份（重复拉起）、父已死的孤儿链、插件名下超长存活的常驻子进程；
- **账本对照**：跨会话任务账本（jobs）与子代理谱系和 OS 进程做指示性对账，账本说在跑却找不到进程、或进程无主，都会被点名；
- **守卫式树杀**：`taskkill /T` 前做创建时间预检（防 pid 复用）、系统进程与自身树白名单拒绝、UI 二次确认，杀后复查；
- **插件审计**：从命令行的 `node_modules/<pkg>` 路径归因，回答"每个插件在机器上养了哪些常驻进程"。

## 安装

```sh
dsh plugin --profile web add dsh-treekeeper
```

## 使用

装好后 Web 界面左下角出现「🌳 TreeKeeper」悬浮按钮，打开面板：

- **泄漏告警**：重复 / 孤儿 / 超长存活三类发现，带证据；
- **未归属进程**：不属于 harness 已知根的进程桶——泄漏最常藏的地方；
- **任务账本**：跨会话的后台任务（官方 jobs 注册表），及其与 OS 进程的指示性对照；
- 每行「树杀」按钮：两次点击 + 系统确认框，服务端再做创建时间与白名单守卫。

## 安全模型

- `/api` 路由同源守卫：Fetch Metadata + Origin + loopback Host 三重校验（关掉 DNS rebinding）；
- 变更动作仅接受 POST；树杀有服务端守卫（白名单 / 系统进程黑名单 / pid 复用预检），并写入本地历史；
- 本插件**只读采样 + 显式杀进程**，不读取会话正文，不外传任何数据。

## 平台

Windows 优先（CIM 采样；不可用时自动降级 `tasklist`，此时归属停用并明示）。macOS/Linux 采样在路线图上。

## 已知边界

- job 与 OS 进程的关联是**指示性**的（官方 `JobSnapshot` 不含 pid）——UI 会标注，绝不据此自动杀进程；
- 绕过 `ctx.subprocess` 直接创建的进程只能由 OS 层兜底可见。
